# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Jekyll static site (Valerio Casalino's blog), hosted on GitHub Pages. It is a single Jekyll-generated site (posts, pages, layouts, includes, assets) — there is no separate untemplated static page anymore (the old `links/index.html` link-in-bio page and the later `/about/` page were both removed; the homepage is now the presentation page and carries the contact links).

There is no build tooling in the repo (no `package.json`, no committed `Gemfile` — it's gitignored). Content is edited either directly as Markdown/YAML or through [Pages CMS](https://pagescms.org), a web-based editor configured by `.pages.yml`; commits made through that UI show up as "Update .pages.yml (via Pages CMS)" — don't be surprised by that commit message pattern in `git log`.

## Commands

Standard Jekyll workflow (Ruby/Bundler must be installed locally; there's no lockfile committed):

```sh
bundle install
bundle exec jekyll serve   # local dev server with live rebuild
bundle exec jekyll build   # production build into _site/
```

There is no test suite, linter, or CI configured in this repo.

## Content architecture

**Posts** live in `_posts/`, named `YYYY-MM-DD-title.md`. `_config.yml` applies `layout: post` and permalink `/blog/:title/` to everything under `_posts` by default, so individual post front matter only strictly needs `categories`. In practice always set an explicit `title` too — Jekyll otherwise titleizes the filename slug for `page.title` (used in `<title>`, OG/JSON-LD, the homepage list, and the Atom feed), which reads badly for anything with an acronym or product name (e.g. `nuclei-can-now-speak-ad.md` would title itself "Nuclei Can Now Speak Ad" instead of "...AD"). Always set an explicit `description` too — it's the meta-description (and `og:description`/JSON-LD `description`), and it's also what `llms.txt` (below) puts next to the post's title, so a missing one falls back to a truncated `page.excerpt`, which is often just the post's opening words out of context (e.g. a writeup that opens with "As always, nmap") and misrepresents the post everywhere it's used:

```yaml
---
title: "Nuclei Can Now Speak AD"
description: "One sentence summarizing the post, used as the meta description when the opening paragraph doesn't work as one."
categories:
  - dev
  - research
---
```

**Layouts** (`_layouts/`):
- `home.html` — the homepage / presentation page (`index.md` uses `layout: home`, no `title` so `<title>` is just the site title + description). Renders a hero on the page background (the name as big display type, the role, and a tilted square portrait from `_data/author.yml`), then a paper card styled as a terminal: a `5amu:~$ cat whoami.txt` command line (`site.title` as the prompt) followed by `{{content}}` as its output — the intro text lives as plain Markdown in `index.md` so it's editable there — plus an accent-colored "read the blog" button and the contact links as chips (each with its `icon` from `_data/author.yml`, rendered via `icon.html`), then "Experience" (see below), then "Skills": one paper card sized to roughly match the experience section, a short pitch with a "browse the skills" button beside a `5amu:~$ ls skills/` listing of up to 8 skill names in two columns (on narrow screens the pitch and the listing stack; skipped when there are no skills), then "Latest writing": the 3 latest posts as `post-card.html` cards (the first one `featured`, spanning both grid columns). Both blog links on the page deliberately share the "read the blog" label. The bio partial is skipped on this layout (`header.html` checks `page.layout == "home"`) since the hero replaces it.
- `blog.html` — the post index at `/blog/` (`blog.md` uses `layout: blog`). Renders `page.title` as an `<h1>`, the search box and tag filter (`list-filter.html`, tags collected from every post's `categories`), and a 2-column grid (`ul.post-grid#post-list`) of `site.posts` as `post-card.html` cards with `filterable=true` (the `#category` tags become filter buttons). The search/filter JS (`list-filter-script.html` with `index="/search.json"` for full-text search) only relies on `#post-list li[data-url][data-tags]` and `[data-tag]` buttons, so keep those if the card markup changes.
- `post.html` — individual post pages. Renders tags/title/date on the page background (plus a tilted header thumbnail if `page.image` is set), then `{{content}}` on a paper card (`.card.content`), then loads Mermaid (theme picked from the toggle's `data-theme`, falling back to `prefers-color-scheme`) (see below) via an inline `<script type="module">`.
- `skills.html` — the skill catalogue at `/skills/` (`skills.md` uses `layout: skills`, no body). Renders the same search box and tag filter as the blog (tags collected from the skill pages' `tags`), then every page with `layout: skill`, sorted by title, as a card with the summary, its `#tag` filter buttons, the install command and links to the skill page and raw `SKILL.md`. There's no search index fetch: each card carries its title, tags, summary and `SKILL.md` body in a `data-search` attribute. See "Agent skills" below.
- `skill.html` — one skill's page at `/skills/<name>/`: a "back to skills" button above and below the article, then the summary, install command and a raw `SKILL.md` link, then the `SKILL.md` body rendered on a paper card. `skill-md.html` and `skill-index.html` are the matching non-HTML layouts that emit the raw `SKILL.md` and the discovery `index.json`.
- `page.html` — generic content pages (currently unused since `about.md` was removed). Renders `page.title` as an `<h1>` then `{{content}}`, no date/tags/Mermaid. Reuses the `.card.content` paper treatment.

**Includes** (`_includes/`) are shared partials: `head.html` (stylesheets, plus a `preload` for the two critical font files and the light/dark `theme-color` metas: keep those font URLs in sync with `style.css`'s `@font-face`, and the theme-color values in sync with `--field`; the toggle script in `header.html` rewrites theme-color when the theme is forced), `header.html` (a "skip to content" link to `#main`, so every layout's `<main>` must keep `id="main"`, then a sticky pill-shaped nav: avatar + prompt-style title — `page.prompt` if set (e.g. `5amu:~/blog$ cd ..` on `blog.md`), else `5amu:~/blog/<slug>$ cd ../..` on posts, `5amu:~/skills/<name>$ cd ../..` on skill pages, else `site.title`, truncated with an ellipsis when too long; always linking home, which is `5amu:~$` — then home / blog / skills links, the current one marked `aria-current="page"`, the light/dark toggle, and a menu button; at 640px and below the links collapse into a dropdown card opened by that button (the CSS collapses them only once the header script adds `.has-menu`, so without JS they stay inline; Escape, an outside click or widening past 640px closes it). The toggle is a `role="switch"` with a fixed `aria-label` ("Dark mode") and `aria-checked` for the state; it stores an override in `localStorage` as `data-theme` on `<html>`.), `footer.html` (a full-width ink band, so every layout includes it *outside* `.wrap`), `bio.html` (reads `_data/author.yml` for the avatar and contact links; a compact card under the header on every page except the homepage), `post-card.html` (one post as a card: thumbnail, date, title, `description` clamped to 3 lines, `#category` tags; params `post`, `featured`, `filterable`, `heading` (the title's tag: `h2` by default, `h3` on the homepage where the cards sit under an `h2`); the whole card is clickable via a stretched link on the title), `icon.html` (inline SVG icon by `name`: Phosphor Icons bold glyphs copied verbatim from `@phosphor-icons/core@2.1.1`, currently `envelope-simple`, `linkedin-logo`, `github-logo`, `arrow-left`, `arrow-right`, `list`, `x`; to add one, copy its `<path>` from that package rather than drawing it, and unknown names render nothing), `list-filter.html` + `list-filter-script.html` (the search box/tag filter markup and its script, shared by the blog and skills indexes; params `list` (the `<ul>` id) and optional `index` (a search JSON URL); items without an index entry match on `data-search`, else their text; the search text and selected tags are mirrored into the URL as `?q=…&tag=…` with `replaceState` and restored on load, and a visually hidden `#search-status` live region announces the match count), `skill-install.html` (the `npx skills add` command box with a copy button, param `name`) and `skill-copy-script.html` (the copy button's click handler, included once per page that shows install boxes; it announces the result through its own live region, since the button's `aria-label` hides its "copied" text). Post pages link back to `/blog/`.

**Post thumbnails and in-body images are supported.** A post can set `image: /assets/img/whatever.png` in its front matter; `post-card.html` renders it as a small bordered square on that post's card (homepage and `/blog/`), `post.html` renders it as a larger header thumbnail on the post page itself, and — because `image` is also the exact front matter key `jekyll-seo-tag`'s `{% seo %}` looks for — it becomes that post's `og:image`/`twitter:image`, i.e. the thumbnail shown when the post is linked on social media or messaging apps. It's exposed as an `image` field (type `image`) in `.pages.yml` so it's pickable from Pages CMS's media browser (media root: `assets`). It's optional — posts without one just show no thumbnail and no link-preview image, there's no generic placeholder graphic or fallback. Post bodies can embed images normally (`![alt](/assets/img/whatever.png)`); `.content img` in `style.css` handles sizing/border/shadow. Contact links in `bio.html` remain plain text (no icon images), and `jemoji` is still not re-enabled — write literal unicode emoji in post bodies instead of `:shortcode:` syntax, since jemoji renders shortcodes as `<img>`. Images live in `assets/img/`; there's no image optimization/resizing pipeline in this repo, so keep files reasonably web-sized before committing them.

**Diagrams can be Mermaid or images** — pick whichever fits the content. Post pages load Mermaid from a CDN (`post.html`) and auto-render any `<div class="mermaid">...</div>` raw-HTML block in the markdown (kramdown passes raw HTML blocks through untouched, which sidesteps Rouge trying and failing to syntax-highlight a "mermaid" fenced code block as a language it doesn't know). See `_posts/2022-10-07-bgp-hijacking.md` for worked examples (sequence and graph diagrams) — that post intentionally keeps its conceptual diagrams as Mermaid (vector, theme-aware) rather than the original raster screenshots, even though other posts now embed raster images directly. This only applies to `post.html` — the homepage doesn't load Mermaid.

**Experience timeline** (homepage) is driven by `_data/experience.yml` (`role`, `company`, optional `url` and `logo`, `start`/`end` as quoted `"YYYY-MM"` strings shown as "Mon YYYY", no `end` = current), ordered by `end` (ongoing entries last), ties broken by `start` and then file position. `home.html` builds a unique `"end|start|index"` string key per entry and sorts those, because Liquid's object sort isn't stable and some roles share months. The right-most card, where the timeline opens, is therefore the ongoing role with the latest start. It's rendered as a horizontally scrolling track of cards, oldest on the left, each snapping to the track's right edge. The inline script at the bottom of `home.html` opens it scrolled fully right (current position), marks the card at the right edge `is-active` with an `IntersectionObserver` (a thin strip near the right edge of the track), and drives the earlier/later arrow buttons and click-to-select; CSS grays out every other card once the script adds `.is-ready`, so without JS all cards stay in color. Company logos live in `assets/img/logos/` (taken from each company's own site: apple-touch-icon or header logo) and are blended into the card with `mix-blend-mode: multiply` in light mode (absorbing the opaque white backgrounds several ship with) and sit on a white plate in dark mode (`--logo-plate`/`--logo-blend` tokens). The section is skipped when the file is empty. Only list real positions there: it's shown as-is on the homepage.

**Agent skills** (`/skills/`) are installable with the [`skills` CLI](https://github.com/vercel-labs/skills): `npx skills add https://5amu.github.io/skills/<name>`. The host in the displayed command comes from `_config.yml`'s `url` (plus `baseurl`), so moving to another domain only means changing `url`; `jekyll serve` swaps in `http://localhost:<port>`, which makes the local command work against the dev server. For a URL with a path, the CLI only looks for a well-known index scoped to that path: it fetches `/skills/<name>/.well-known/agent-skills/index.json` (v1 format: `name`, `description`, `files: ["SKILL.md"]`), then `/skills/<name>/.well-known/agent-skills/<name>/SKILL.md`. Both are relative to the index, so no hostname is baked into the served files. There is deliberately no root `/.well-known/agent-skills/index.json`: a root index without a scoped one makes the CLI fail with "no matching skills", and serving it would need a second copy of each `SKILL.md`.

A skill is two parts:
- `_data/skills/<name>.yml`: what goes into `SKILL.md`. `description` is the trigger text agents read to decide when to load the skill; `body: |` holds the Markdown instructions, indented two spaces. It's a data file on purpose. Jekyll renders every collection document, even with `output: false`, so a `.md` source would come out as HTML. A `.txt` source would still go through Liquid on GitHub Pages' Jekyll 3.10 and silently eat any `{{ }}` in a skill. Data files get neither. The served `SKILL.md` front matter is rebuilt from `name` (the file name), `description` and, when the YAML sets it, `disable-model-invocation: true` (manual-only skill, as interview is); add other keys in `skill-md.html` if a skill ever needs them (e.g. `license`).
- `skills/<name>/`: three front-matter-only stubs, one per output, since GitHub Pages' safe mode allows no generator plugin: `index.html` (`layout: skill`, `skill: <name>`, `title`, `tags` (a list, shown on the catalogue card as filter buttons and on the skill page), and `description`, the human-facing summary that the catalogue, meta description and `llms.txt` use), `index.json` (`layout: skill-index`, permalink `/skills/<name>/.well-known/agent-skills/index.json`) and `SKILL.txt` (`layout: skill-md`, permalink `.../agent-skills/<name>/SKILL.md`; the `.txt` source extension keeps kramdown from converting the output). Copy `skills/unslop/` and change the name in all three.

Only single-file skills are supported (`files: ["SKILL.md"]`); bundled `references/` or scripts would each need another stub and an entry in `files`. `skill.html` undoes kramdown's smart quotes/ellipses/dashes on the rendered body (the source's own literal curly characters are shielded and restored) so the page shows the text as written; keep the summary free of quotes, since jekyll-seo-tag smart-quotes `description` in the meta tags. Check an install end to end against the dev server with `npx skills add http://localhost:4000/skills/<name> -a claude-code -y` in a scratch directory.

**Author/contact info** lives in `_data/author.yml` (name, avatar URL, bio HTML, `contact: [{title, icon, url}]`) and is consumed by `bio.html` (plain text links, no icons) and the homepage (chips with icons; `icon` must be a name `icon.html` knows). `author.yml` isn't exposed in `.pages.yml`, so it's edited by hand.

**Styling**: a neo-brutalist structure modelled on claudecodeclub.ai, but in the site's own original palette: a warm-grey "field" background (`#e2ded4`; dark `#14161a`), lighter "paper" cards (`.card`, `#efece5`, a muted off-white on purpose; dark `#1c1f24`) with a 2.5px ink border and a hard offset shadow (ink in light mode, the mint accent `#4fd1a5` in dark), and the emerald accent (`#0f6b52`; dark `#4fd1a5`) for links, the uppercase-mono buttons (which press down on click), the active nav item, selected tags and the hard text-shadow on big headings. Corners are square everywhere except the pill nav, the toggle, the round menu button and the round avatars. Space Grotesk for display type and IBM Plex Mono for everything else (both self-declared `@font-face` from @fontsource on jsdelivr, latin `unicode-range` so emoji fall through to color-emoji fonts). A single `assets/css/style.css` covers the whole site: tokens on `:root` (`--field`, `--paper`, `--paper-2`, `--ink`, `--muted`, `--line`, `--drop`, `--link`, `--cta`/`--on-cta`, `--title-shadow`, `--code-bg`, `--footer-*`), redefined for dark mode both under `@media (prefers-color-scheme: dark)` (guarded by `:root:not([data-theme="light"])`) and under `:root[data-theme="dark"]` for the manual toggle — keep the two blocks in sync. `assets/css/syntax.css` (Rouge highlighting, loaded only on `post.html`) follows the same light/dark pattern with its own `--syn-*` tokens. Spacing under the sticky nav is `--nav-gap` (50px, the *visible* gap on every page, to the bio card or, on the homepage, to the hero name). Sticky positioning draws the nav `--nav-top` (14px) below its layout slot, so the margins add `--nav-top` back (`#bio` margin, `main.no-bio` padding); change `--nav-gap`, not those margins. Motion: the homepage hero staggers in on load (`.reveal` + `--i`), post cards rise in on scroll via CSS `animation-timeline: view()` where supported; both are disabled under `prefers-reduced-motion`.

**SEO/GEO**: `head.html` renders `{% seo %}` (jekyll-seo-tag) then `{% feed_meta %}` (jekyll-feed's `<link rel="alternate" type="application/atom+xml">` discovery tag — must stay paired with `{% seo %}`, it's easy to add the plugin and forget this tag). `{% seo %}` emits title, meta description, canonical URL, Open Graph/Twitter Card tags, and JSON-LD from `_config.yml`'s `title`/`description`/`url`/`author`/`logo`/`social` keys plus each page's own `title`/`description` front matter:
- `author` (name/email/**url**) feeds the JSON-LD `author` on every page and the Atom feed's author.
- `logo` (the same GitHub avatar URL used in `bio.html`) feeds the JSON-LD `publisher.logo` Google expects on `BlogPosting` rich results.
- `social.name`/`social.links` (sameAs) feed the JSON-LD entity on the homepage only (jekyll-seo-tag's `homepage_or_about?` check) — update `links` if profile URLs change.
- Post type (`BlogPosting`) vs. page type (`WebSite`/`WebPage`) in JSON-LD is inferred automatically from `page.date`, not set explicitly.

`{% seo %}` only reads a page's own `image` front matter key for `og:image`/`twitter:image` — it does **not** fall back to `_config.yml`'s `logo`. Posts get theirs "for free" from their `image` front matter (see the note above about post thumbnails). `index.md` and `blog.md` have no such front matter of their own, so `_config.yml`'s `defaults` sets `image` for those two paths explicitly to the same avatar URL as `logo`/`_data/author.yml`'s `dp` — this is why that URL is duplicated three times across the config; keep them in sync if the avatar changes. Without it, linking the homepage or blog page on social media/WhatsApp would show no preview image at all.

**`robots.txt`** and **`llms.txt`** live at the repo root as Liquid-templated pages (empty `---\n---` front matter, like `search.json`, so Jekyll runs them through Liquid but doesn't markdown-render them since their extension isn't a markdown one). `robots.txt` allows all crawlers and points to both `sitemap.xml` (from jekyll-sitemap) and `llms.txt`; jekyll-sitemap would otherwise auto-generate a bare-bones `robots.txt` itself, but backs off once a source file exists. `llms.txt` follows the [llms.txt convention](https://llmstxt.org) — a plain-Markdown index of the site (Blog and Skills links, every post title/categories/summary, and every skill with its install command) meant for LLMs/generative engines to fetch directly instead of parsing rendered HTML; it loops `site.posts` the same way `blog.html` and `search.json` do, so keep it in sync if that loop's shape changes. Each post's summary line prefers its `description` front matter, falling back to a truncated `excerpt` only if `description` is unset — so every post should carry a `description` (see the note above about post front matter), otherwise its `llms.txt` entry is just the post's opening words out of context, which misrepresents the content.
